# FLAPJACK: a pancake-flipping game running on a CPU built entirely from NAND gates, simulated gate by gate, in one HTML file

Studio rules (Xinu): **one self-contained HTML file, zero dependencies, offline, no network requests, no `eval`, no `new Function`, no `innerHTML` with generated data (DOM builders and text nodes only), no external fonts, no libraries.** Anything lifted from elsewhere is inlined with a provenance comment and listed in `LIFTS.md`. Browser storage, if used at all, is wrapped in try/catch and the page must work without it. **Do not predict, summarize or rank results anywhere in code, docs or UI.** Report only what the tests exercise.

This spec is deliberately enormous. Build as much of it as you can, in the order given, and **say so in REPORT.md and leave a part failing** if you cannot complete it. A part that is stubbed, faked, or quietly replaced by something easier is worse than a part that is missing and reported missing.

## 0. What you are building, in one breath

A virtual 16-bit computer whose processor exists only as a **netlist of NAND gates** (nothing else is a primitive), a **silicon compiler** in JS that generates that netlist from structural descriptions, a **gate-level simulator** that runs it, an **instruction-level twin** that must agree with it in lockstep, an **assembler**, a **game** written in that assembly, a **time-travel debugger**, a **power heatmap**, a **fault-injection lab**, a **one-bit sound card**, and a **test panel** that proves all of it, all inside a single HTML file. Yes, really.

## 1. Names (use these, they are load-bearing for the audit)

| Part | Name | One-line job |
|---|---|---|
| Netlist generator | **Batter** | builds the gates from structural descriptions |
| Gate simulator | **Griddle** | settles and clocks the netlist |
| Instruction-level twin | **Pan** | behavioural CPU, independent code path |
| Assembler | **Whisk** | two-pass assembler for the ISA |
| Time-travel debugger | **Spatula** | steps and scrubs backward and forward |
| Power heatmap | **Syrup** | counts gate toggles per block |
| Fault lab | **Burnt Edges** | injects faults in memory, never in the shipped build |
| Test panel | **Taste Test** | numbered suites, all runnable from the page |

## 2. The machine (exact, no freedom here)

- **Word:** 16 bits. **Registers:** R0..R7, R0 reads as zero (writes ignored). **PC:** 16 bits. **Flags:** Z, N, C, V.
- **Memory:** 65,536 words, word-addressed. **Memory is the one component allowed to be behavioural** (an array behind an address bus and a data bus, with a read-enable and a write-enable driven by gates). Everything else, including the PC, registers, ALU, decoder, sequencer and bus logic, must be NAND gates.
- **Flip-flops are forbidden as primitives.** Build level-sensitive latches and master-slave edge-triggered D flip-flops out of NANDs (feedback loops are expected). The simulator must detect and report an oscillating or non-settling network instead of hanging.
- **Clock:** a single phase. One *cycle* = one clock edge plus settling. The CPU is multi-cycle; define how many cycles each instruction takes and publish the table (§3).
- **Memory map:** `0x0000-0xDFFF` RAM; `0xE000-0xEBFF` video (64×48 pixels = 3,072 words, one 4-bit colour per word's low nibble, row-major); `0xF000` keyboard (read: bitmask of held keys; see §8); `0xF001` free-running 16-bit cycle counter (read-only); `0xF002` speaker (write bit 0); `0xF003` halt (write any value halts the machine and raises the `halted` flag). Reading an unmapped address returns `0xFFFF`.

## 3. The ISA (24 instructions, fixed encoding)

Every instruction is one 16-bit word, optionally followed by one 16-bit immediate word. Publish the exact bit layout and the cycles-per-instruction table in `ISA.md` **before** building anything else, and generate Whisk's tables from it.

`NOP, HLT, MOV, LDI, LD, ST, ADD, ADC, SUB, SBC, AND, OR, XOR, NOT, SHL, SHR, SAR, CMP, JMP, JZ, JNZ, JN, JC, CALL, RET, PUSH, POP`

`SHL`/`SHR`/`SAR` shift by one bit per instruction; there is no barrel shifter and no multiplier. The stack pointer is R7 and grows downward. `CALL` pushes the return address; `RET` pops it. All arithmetic sets flags as you define in `ISA.md`, and you must say what `CMP` leaves in each of Z, N, C, V.

## 4. Batter (the silicon compiler)

- The netlist is **generated by code from structural descriptions**, not hand-listed: half adder → full adder → 16-bit ripple-carry adder → ALU slice → ALU; mux2 → mux4 → mux8; latch → flip-flop → register → register file with two read ports and one write port; decoder; sequencer (a ring or counter built from your flip-flops); and so on.
- Batter emits the netlist as a flat array in a documented format (gate id, input ids, output id), plus a **block map**: every gate belongs to a named block, nested (`cpu/alu/adder/bit7/carry`).
- Batter prints a **build report**: total NAND count, count per top-level block, number of flip-flops, and the **critical-path depth in gates** from any flip-flop output to any flip-flop input. Report the numbers you actually computed.
- The netlist must be **deterministic**: building twice produces byte-identical output, and the page shows its SHA-256 (write your own SHA-256 in JS; do not use `crypto.subtle`, which is not available on `file://` in all browsers).

## 5. Griddle (the gate simulator)

- Event-driven or levelized, your choice, but it must (a) settle combinational logic after every input change, (b) update flip-flops on the clock edge with correct master-slave behaviour, (c) detect non-settling networks after a bounded number of passes and **report them**, and (d) run with **no call into Pan or any behavioural model** (see §14).
- Griddle exposes: step one cycle, step one instruction (until the sequencer's *retire* output goes high), run N instructions, run until halt, and reset.
- Griddle counts **toggles per gate** (for Syrup) and **gate evaluations per second** (for the report).

## 6. Pan (the instruction-level twin)

- An independent, straightforward behavioural CPU implementing the ISA as written in `ISA.md`. **Pan must not share code with Batter or Griddle.** Different author mindset, different file region, different data structures.
- **Lockstep (`diff`):** run Griddle and Pan together. After **every retired instruction**, compare PC, R0..R7, flags, and a running FNV-1a hash of all memory writes since reset. On the first mismatch, stop and print the cycle number, instruction, expected state, actual state, and the last 16 retired instructions. **Lockstep is a feature of the page**, not just a test.
- Pan runs standalone at full speed in "fast mode". Report instructions per second for each of Pan and Griddle on the machine the report was generated on.

## 7. Whisk (the assembler)

- Two-pass. Labels, numeric literals in decimal/hex/binary/char, `.org`, `.word`, `.string`, `.equ`, and **simple macros with parameters** (`.macro` / `.endm`). Errors report file line, column and a human sentence.
- Whisk emits a **listing** (address, words, source line) and a symbol table. The page must let the user paste assembly, assemble it, and load it into either machine.
- **Round trip:** a disassembler (also in the page) must disassemble Whisk's output back to text that re-assembles to **byte-identical** words, for the whole game and for a 2,000-instruction random-valid-program fuzz seeded from a fixed seed.

## 8. The game: PANCAKE

Written **in assembly for this CPU**, assembled by Whisk, and run by Griddle (and by Pan). It is not written in JS and ported; there must be no JS game logic anywhere except the keyboard and video plumbing around the machine.

- A pan with a pancake above it. Arrow-left/right (keyboard word bits 0/1) move the pan; space (bit 2) flips. The pancake follows **fixed-point 8.8 physics** (gravity, flip impulse, landing, a bounce, a burn timer based on time on the same side), with a **xorshift16 RNG** seeded from a constant for the very first pancake and from the cycle counter after that.
- Scoring: flips caught, sides cooked evenly, a "burnt" lose-state with a visible char colour. 64×48 video, 16 colours defined by a table in your code (publish it).
- **Demo mode:** a fixed **input tape** (a list of key states per frame, stored in the page) drives the game for 600 frames with no user input. The tape and the final video-frame hash are published in `DEMO.md`.
- The game must run **correctly in both machines**: after 600 frames the video memory hashes (FNV-1a over all 3,072 video words) must match between Griddle and Pan.

## 9. Spatula (time-travel debugger)

- Step forward one instruction; **step backward one instruction**; **scrub** to any retired-instruction index between 0 and the furthest reached.
- You may not store every state. Use **checkpoints every 4,096 retired instructions** plus deterministic replay. Report the memory the history actually uses after a 100,000-instruction run.
- **Reversibility test:** run forward 20,000 instructions recording the state hash after each; then step backward to 0, comparing the hash at every step; then forward again. All hashes must match exactly.
- The UI shows registers, flags, a memory viewer, the disassembly around PC, and a one-line plain-language description of the last instruction.

## 10. Syrup (power heatmap)

- A live panel showing the **block map as nested rectangles** coloured by toggle count per cycle (a normalised heat colour). A "joules" counter is toggles × a constant that you name and justify in a comment.
- Report the **hottest three blocks** during the demo run, from your own counters. Do not claim they are hot in any docs; show the numbers.

## 11. Burnt Edges (the fault lab) — **never in the shipped build**

- The shipped HTML has **no fault switches, no mutant flags, no debug backdoors**. A static scan in the test suite proves it.
- The **tests** inject faults **in memory** into a copy of the netlist: at least **24** distinct faults including stuck-at-0 and stuck-at-1 on selected gates, swapped inputs, an inverted output, a missing carry in one bit, a flip-flop that never clocks, a swapped pair of register-file read-mux inputs, and a stuck bit in the PC.
- For each fault, run lockstep over the demo program and report **whether it was caught and after how many retired instructions**. A fault that is never caught is **reported, not hidden**; do not weaken the oracle to catch it.
- Include at least **two control faults you expect to be invisible** (for example a gate that is unreachable from any output) so that the lab proves it can say "not caught" when that is correct.

## 12. Sound

- Writes to `0xF002` toggle a one-bit speaker. The page plays it through the Web Audio API in real time **and** can render it **offline** to a WAV byte array (PCM, mono, 22,050 Hz, the toggle timeline resampled deterministically) with an embedded **CRC-32** you compute yourself.
- The game plays a jingle on a catch and a different one on a burn. The WAV CRC for the 600-frame demo is published in `DEMO.md`.
- If audio cannot start (autoplay policy), the page must say so in text, not fail silently.

## 13. Taste Test (the in-page test panel)

A panel in the page, opened by a button, that runs **at least 40 numbered suites** within a stated time budget on a mid-range laptop and shows pass/fail with the measured numbers. The same suites must run headlessly with **Node and no packages** from a `tests/` folder (`node tests/run-all.js`), reading the HTML file and extracting the scripts you wrote, and writing `results.jsonl` with a hash of the HTML file and of each suite's input. It must include, at minimum:

1. Batter determinism (build twice, identical hash).
2. Gate census matches the report.
3. Flip-flop, latch and register unit tests against truth tables.
4. ALU exhaustive test on 8-bit slices (all 65,536 inputs) and 100,000 random 16-bit cases against an independent oracle.
5. Every instruction against Pan, one by one, with edge cases (overflow, borrow, shift out, stack wrap).
6. Whisk: all directives, error messages, macro expansion, and the round trip from §7.
7. Griddle: oscillating-network detection (a deliberate ring of three NANDs).
8. Lockstep over the demo program, whole run.
9. **Perturbation test:** change one gate in the adder in memory; the demo's video hash **must change**; revert; it **must change back**.
10. **Independence test:** statically show that Griddle's code path does not reference Pan or its data (a scan with a stated method, plus a runtime check that Pan is never called while gate mode runs).
11. Spatula reversibility (§9).
12. WAV length, CRC and determinism (§12).
13. The fault-lab table (§11), with the two control faults.
14. Static scan: no network calls, no `eval`, no `new Function`, no `innerHTML` assignment from generated strings, no mutant switches, no external URLs except in comments.
15. Reproducibility: all seeds are constants; two runs give identical `results.jsonl` content except for timing fields.

## 14. Forbidden (named cheats)

- Precomputed frames, precomputed instruction results, or a table of expected hashes consulted at run time.
- Any behavioural ALU, decoder, register file or sequencer in the gate-mode path. Using JS `+`, `-`, `&`, `|`, `^`, `<<` or `>>` on CPU data **inside Griddle's evaluation of the CPU** is forbidden. (Griddle may use them for bookkeeping that is not CPU data.)
- Griddle calling Pan, sharing a data structure with Pan, or reading Pan's registers.
- Pan calling Griddle or reading its state.
- Branching on the game's name, on a hash of the program, or on the demo tape.
- Using the game to hide gaps: the game must exercise the ISA, and the tests must run the ISA tests independently of the game.
- A "self-host" shortcut: nothing may embed a final output so the page can show it without computing it.
- Claiming a test passes in prose that the test does not actually check.

## 15. Deliverables

- `flapjack.html` — the single file.
- `tests/` — Node-only suites and `run-all.js`, plus `results.jsonl`.
- `ISA.md`, `DEMO.md`, `LIFTS.md`, `REPORT.md`.
- **REPORT.md must say, for every numbered part of this spec, one of: built and tested (name the suites), built and not fully tested (say what is missing), not built.** Measured numbers go in tables, not sentences. Use the words **Measured:** and **Hypothesis:** so the reader can tell them apart. "Inconclusive" does not mean "equivalent."
- A "known gaps" section. If the spec contradicts itself, **say where, and what you did instead.** (It contradicts itself at least once, on purpose. Catch it, say so, and record what you did instead.)

## 16. Style

Small, readable functions. Comments say *why*. The UI is clear and a little charming: this is a pancake game. Keyboard and mouse both work. The page loads fast and does nothing until the user asks (no autoplay, no startup sound). Every number on screen is a measurement or a labelled constant.
